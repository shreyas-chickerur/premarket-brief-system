# Daily trading procedure

The canonical Stage 0–6 procedure, followed verbatim by two different
callers: the 06:20 Central scheduled routine (the first attempt of the day),
and `WATCHDOG_PROCEDURE.md`'s self-heal retry (re-run once, after a diagnosis
and possible fix, if the first attempt aborted). See `PROCEDURE_RATIONALE.md`
for why each rule below exists.

Two placeholders must be substituted by whoever invokes this procedure
before following it: `{{DRIVE_FOLDER_ID}}` (the Drive folder holding
`state.json`, the dated `journal-*.json` files, and the dated
`run-manifest-*.json` files) and `{{STATE_FILE_ID}}` (the Drive file id of
the current `state.json`). Both live only in the trigger configs, never in
this repository — see `HANDOFF.private.md`.

**STAGE 0 — PREFLIGHT. Do this before looking at a single price.**

**THIS IS A DRY RUN. Place no orders of any kind. `review_equity_order` and `cancel_equity_order` are permitted; `place_equity_order` is FORBIDDEN regardless of what any later stage says. In Stage 5, compute and report every order you would have placed — symbol, side, quantity, limit, stop, resulting weight — and place none of them. Pass `prefix="[DRY RUN]"` to the email renderer.**

0. Create the run log first, before anything else: `log = runlog.RunLog(run_id, mode=...)`. Record every check, stage, external call, anomaly, and decision on it as you go — including deliberate non-actions. Its `.manifest()` is what the stored manifest is built from. **Wrap each numbered stage's own work in `with log.stage(name):`, using exactly the name `runlog.STAGE_TIMING_BUDGETS_MS` uses for it** (`"preflight"`, `"evidence_review"`, `"prior_day_review"`, `"gather"`, `"measure"`, `"gate"`, `"individual_account"`, `"agentic_account"`, `"record_and_send"`, for Stages 0 through 6 in order) — an unbudgeted or misspelled name is not an error, but it does mean that stage's timing goes unmonitored in Stage 6's "System health" section.

**After every `with log.stage(name):` block exits, write `runlog.heartbeat_payload(log)` to a NEW file, `run-heartbeat-YYYY-MM-DD-{len(log.stages)}.json`, in the Drive folder — `create_file` every time, never `update_file`.** The connector can create a file but not modify one already written (the same reason `journal-*.json`/`splits-cache-*.json`/etc. are all create-only), so "update the heartbeat" means a new, higher-numbered file each stage, not editing the last one — `len(log.stages)` is already exactly the right number (0 for the very first write, before any stage has completed, then 1, 2, 3... as each one does) and needs no separate counter. This is what lets `watchdog.py` tell a run that is still legitimately working apart from one that has actually stopped responding — see step 1b for the first write and PROCEDURE_RATIONALE.md, 5 September 2026, for why per-stage budgets alone were never enough (they are advisory; nothing before this stopped a stage that ran long, and the watchdog cannot see the difference between "slow" and "stuck" without something like this to read). Old heartbeat files are never deleted (the connector cannot reliably delete either) — expected leftover clutter, exactly like old daily journal files left behind after monthly compaction, not an error.

**Also after every stage, before starting the next one, check the wall-clock deadline: if `log.elapsed_seconds() > state["config"].get("run_wall_clock_deadline_seconds", runlog.DEFAULT_WALL_CLOCK_DEADLINE_SECONDS)`, stop advancing stages.** Call `log.abort(f"wall_clock_deadline_exceeded after stage {log.last_stage_name()}")` and go straight to Stage 6 — write the manifest and send the email with whatever was gathered so far, rather than continuing into the watchdog's own window. This is a proactive self-stop for a run that is genuinely slow but still executing normally; it CANNOT catch a single hung external call that never returns (the deadline check itself never runs until the call it's waiting on does) — the heartbeat above is what catches that case, from outside, once this run has gone quiet for longer than any stage should legitimately take.

- `congress-discovery-cache-YYYY-MM-DD[-N].json` — a bare JSON list, one object per bioguide_id checked this run: `{"bioguide_id":, "checked_through": today, "symbols": [...]}` — the symbols `congress_trade_items_by_politician` discovered for that member, at `ledger.CONGRESS_DISCOVERY_HORIZON_DAYS` (weekly) cadence. Skip this file only when `bioguides_needing_discovery_check` returned nothing to check this run.

**These five dated files are the append-only audit trail. They are written every run exactly as above, unchanged — but as of 11 September 2026 they are no longer what tomorrow's run reads.** That is the sixth file below.

- `state-bundle-YYYY-MM-DD-{run_seq}-{chunk_seq}-of-{chunk_count}.json` — **NOT written here. See the last paragraph of this stage** (the refresh runs after the email, and only when `ledger.state_bundle_needs_rewrite` says the bundle is stale).

**After attempting each of the four dated cache-file writes above (fills, splits, sector, congress-discovery), record whether it actually happened: `log.check(f"{cache}_cache_written", <the create_file call actually returned a file, OR the list to write was empty>, "warn", detail=...)`.** This is not optional bookkeeping — 8 September 2026, a watchdog-retry run computed `fills_ready_to_cache` as 870 real, cache-ready fills (logged in its own `metrics`) and then never issued the `create_file` call for `fills-cache-2026-09-08.json` at all, while the adjacent `splits-cache` write in the very same run succeeded. Nothing on that run's own manifest recorded the miss, so it surfaced only when a human went looking at the next morning's still-slow preflight and diffed the run's `calls` log by hand. A `warn` check that fails specifically WHEN there was something to cache and no matching `create_file` call was made turns that same gap into a same-day, visible finding — and, via `no_chronic_failures`, an unmissable one if it ever recurs. The state bundle is recorded separately: `early_state_bundle_written` at step 7b when one was written, and `state_bundle_fresh` at step 6c every run.


**Who is running this procedure changes what happens next:**

- **If the 06:20 scheduled routine fired this directly** and the run **ABORTED**: do not render or send any email. Write the manifest and journal as above and stop. The watchdog owns deciding what happens next.
- **If the run SUCCEEDED or the market was CLOSED**, or **if you are the watchdog re-running this procedure after a diagnosis/fix attempt**: render and send the email now. This is the only place email-sending logic lives; both callers funnel through it.

**There is one call that both renders and verifies — `emailer.render_email` — and no other path to send an email.** It takes `agentic_ideas`/`suggestion_ideas` as structured data, not pre-rendered HTML, and runs `emailer.verify_email` on them internally, unconditionally, before anything renders. **This is deliberate: `verify_email` used to be a separate call a caller had to remember to make, which is exactly the "documented intention, nothing checked" failure this system keeps getting burned by (the journal's `unreadable` list, the dead `find_optimizations` findings, the research coverage conflation). There is no argument to `render_email` that accepts pre-built account-section HTML, so skipping verification is not something this call can express.** It raises `ValueError` — do not catch it and send anyway — on a `buy`/`sell`/`trim` card with no parseable quantity at all (10 September 2026: "how much" must be a real number, not a phrase like "partial trim"), a card's numbers not matching the recorded decision, an empty-source bullet, a bullet citing a source outside the research bundle and `emailer.ALLOWED_SOURCE_PREFIXES`, or a numeric claim (a price, a percentage, anything not a date or ordinal) that cannot be traced to the manifest, the research bundle, or a broker response. If it raises, that is a bug in what was built for the email, not a false alarm to route around; fix the underlying card or bullet, do not weaken the check.

**The one section left, "System health," still keeps to `emailer.OTHER_SECTIONS` — at most 1, its title exactly `"System health"`, never one of the two account titles (those come from `agentic_ideas`/`suggestion_ideas`, never from `other_sections`).** `render_email` raises `ValueError` on a violation — enforced in code, not just this prose, specifically so the section list cannot silently grow again the way it did before (four sections cut to three on 1 September 2026, five cut back to three on 10 September 2026). Passing nothing for `other_sections` is fine — the code-computed tally line under "System health" always renders regardless.

- **"Agentic account — activity"**: build `agentic_ideas` as a list of dicts, one per symbol touched this run (or, under the DRY RUN guard, one per order that *would* have been placed) — `{"symbol": ..., "action": "buy"|"sell"|"trim"|"hold", "quantity": "2 shares", "detail": "limit 61.80, stop 58.09, 12.48% weight", "bullets": [(text, source), ...]}`. **For `buy`/`sell`/`trim`, `quantity` must state the actual number — the share count, and the dollar amount where one was computed (`"2.97 shares, ~$1,127"`, not `"partial trim"` or any other phrase with no number in it).** `emailer.verify_email` enforces this (`emailer.ACTIONS_REQUIRING_QUANTITY`) and raises rather than send a card that cannot answer "how much" — if the exact figure already exists in a `runlog.Decision`'s `reason` text or `inputs`, as it usually does, use that one, do not restate it vaguely. Every bullet is one concrete reason the idea moved in the direction of the call, each tagged with the specific source that supports it. Include existing held positions too (`action: "hold"`), briefly, with the broker's actual response as a bullet where an order was really sent. When `agentic_ideas` is empty, `agentic_closest_calls` reports the rejected idea(s) that got furthest through the gate instead of bare "Nothing today." — this is only visible at all when Stage 3 set `gate_failed` to one of `runlog.GATE_CONDITIONS`'s exact strings.
- **"Individual account — suggestions"**: same `idea_card` shape and the same required-quantity rule above, one card per idea that cleared the gate in Stage 4 — symbol, buy or sell, how many shares (and dollars), and bullets sourced the same way as above. Skip anything that didn't clear the gate; an empty `suggestion_ideas` on a do-nothing day renders "Nothing today.", or the closest call(s) when any rejection reached the gate at all.
- **"System health"** (rewritten 10 September 2026, at the reader's own request — the previous version was a dump of check names and internal metrics nobody outside this codebase could parse): 2–4 short sentences, in plain English, for a reader who does not know what a "fills cache" or a "wall-clock budget" is. `emailer._health_line` already prints the one thing that is always mechanically true (how long the run took, how many internal checks passed) above whatever is written here — this section is for judgment and translation, not restating numbers. Answer, in order: **(1)** did today's run work — cleanly, with something minor worth knowing, or did something go wrong; **(2)** if there is anything worth knowing, what it means in practice, never the mechanism — "today's research was cut short by a time limit, so fewer stocks were reviewed than usual" is right, "Stage 0 consumed 641s of the 2700s wall-clock budget, so per-symbol research feeds were not issued for the researched set" is wrong, even though both describe the same fact; **(3)** only when this run was a watchdog retry, one plain sentence on what was found and fixed — "a bug in how trade records were saved was found and fixed automatically; no action needed from you," never a commit hash or a function name. Everything else this run computes — `runlog.stage_budget_overruns`, the universe funnel, `runlog.gate_funnel`, the brokerage-token forecast, `correlation_concentration`, the Stage 0.5/0.6 evidence and prior-day-review verdicts — is still recorded in full on the run log and journal (`log.metric(...)`, per those stages' own instructions) for anyone auditing the system directly; none of it belongs in this section unless it is something the reader needs to act on or reassures them nothing is wrong. If nothing is worth saying beyond "ran cleanly," say exactly that in one sentence — do not pad it out to look thorough. **`runlog.stage0_capacity_forecast` (step 9b) is explicitly one of the things that belongs here whenever it warns** — this is the check that exists specifically so the reader hears "the daily setup step is running low on time again, worth compacting the trade history soon" several days before it actually fails a run, not only after (`PROCEDURE_RATIONALE.md` Stage 7). A `warn` from it is not optional flavour text like a quiet day's other metrics; treat it the same as the brokerage-token forecast warning — say it, in plain English, every day it fires, until it stops.

The renderer still supplies the verdict banner, the code-computed health tally, and the footer, and still escapes everything passed to it — write plain prose, no markup. Send with Gmail as **HTML** (`contentType: text/html`) using the returned `subject` and `html`, to `state.json.config.email_to`.
